# Plan 01-05: Admin dashboard + product list (with delete confirm)

<goal>
Build the two pages the admin lands on after signing in: the dashboard
at `/admin` (real numbers from `getAdminStats()`, no fabricated metrics,
brand-voice helper copy, honest empty state) and the product list at
`/admin/products` (shadcn `Table` with thumbnail / name / section / group
/ price / updated / actions; row hover state from the UI-SPEC palette;
delete via shadcn `AlertDialog` with the "Remove {product name}?" copy).
This plan installs the remaining shadcn primitives the product CRUD
needs (table, dialog, alert-dialog, dropdown-menu); the form-specific
primitives (tabs, select, textarea) come in Plan 01-06 alongside the
form itself.

</goal>

<context>
Per `01-CONTEXT.md` D-14 (`/admin` dashboard, `/admin/products` list as
the entry points), D-15 (table with name, section, group, price, primary
image thumbnail; edit/delete actions; delete via confirm dialog — no
separate `/products/[id]/delete` route), D-19 (`getAdminStats()` from
`lib/admin.ts` for total/per-section/per-group counts and backend
connection status), and D-21/D-22 (anti-slop design, 16px inputs,
WCAG AA, reduced-motion respect). The full visual and copy contract is
in `01-UI-SPEC.md` §Dashboard and §Products list.

`lib/admin.ts:13-42` already returns the right shape — total, bySection,
categoryCounts, connected, error — but uses a relative
`fetch('/api/admin/products')` that doesn't work in server components
(Pitfall 6 in `01-RESEARCH.md:888-893`). Plan 01-07 (storefront
migration) switches `getAdminStats` to `backendFetch` directly; for now,
this plan can use it as-is because the dashboard is the consumer and the
bug will not block rendering. The executor should note that the
`connected: false` fallback fires when the backend is unreachable
(which is the honest empty state per D-12).

The shadcn primitives installed in Plan 01-03 (button, input, label,
card) cover the dashboard and the table's row buttons. The new
primitives in this plan are: `table` (for the row markup), `alert-dialog`
(for the delete confirm), `dialog` (required dependency of
`alert-dialog`), and `dropdown-menu` (for the per-row `•••` action menu
per UI-SPEC §Products list).

The product form (create + edit) is built in Plan 01-06; this plan only
needs the list view and the delete action.

</context>

or any other fabricated telemetry. The dashboard is honest about the
counts it knows and silent about the rest.

The body maps over `products` into `<TableRow key={p.id} className="hover:bg-[rgba(26,24,20,0.03)]">` containing, in order: a `<TableCell>` with the 40x40 image thumbnail (`<img src={p.image} alt={p.name} className="w-10 h-10 object-cover rounded" />`) followed by the name as a `<Link href={`/admin/products/${p.id}`} className="text-[#1A1814] hover:underline font-medium">{p.name}</Link>`; a `<TableCell className="capitalize">{p.section}</TableCell>`; a `<TableCell className="capitalize">{p.group}</TableCell>`; a `<TableCell className="text-right tabular-nums">${p.price.toFixed(2)}</TableCell>`; a `<TableCell className="text-[rgba(26,24,20,0.6)] text-[13px]">—</TableCell>` (updatedAt is not currently on the `Product` type — leave a muted em-dash for now; the backend returns `updatedAt` in the JSON but the frontend type does not); and a `<TableCell>` with a `<DropdownMenu>` whose `DropdownMenuTrigger` is `<Button variant="ghost" size="icon" className="h-8 w-8"><MoreHorizontal className="h-4 w-4" /></Button>`. The dropdown content has two items: `<DropdownMenuItem onSelect={() => router.push(`/admin/products/${p.id}`)}>Edit</DropdownMenuItem>` and `<DropdownMenuItem onSelect={() => setPendingDelete(p)} className="text-[#8B2E1F]">Remove</DropdownMenuItem>`.

3. The `AlertDialog` (from `components/ui/alert-dialog.tsx`) lives at the same render level, controlled by `pendingDelete`: when it is non-null, render `<AlertDialog open={!!pendingDelete} onOpenChange={(open) => !open && setPendingDelete(null)}><AlertDialogContent>...` with the UI-SPEC §Delete dialog copy: title "Remove {pendingDelete.name}?", body "This will take the product off the storefront immediately. The `onClick` on the confirm button calls `async () => { const res = await fetch(`/api/admin/products/${pendingDelete.id}`, { method: 'DELETE' }); if (res.ok) { toast.success('Removed.'); router.refresh(); } else { toast.error('Couldn\'t remove. Try again.'); } setPendingDelete(null); }`.

4. Hand-rolled minimal toast: in the same file (or in a tiny sibling
`components/admin/toast.tsx` if you prefer a separate module — pick ONE
and stay consistent), export `useAdminToast` which is a `useState`-based
hook returning `{ success: (msg: string) => void, error: (msg: string) =>

the bottom of the page (`fixed bottom-6 right-6 z-50 flex flex-col gap-2`)
managed by a top-level `<ToastContext.Provider value={...}>` at the
component root, with messages auto-dismissing after 2.6 seconds via
`setTimeout`. This satisfies the "hand-rolled minimal toast" discretion
area in `01-CONTEXT.md:64` without pulling in `sonner`.
