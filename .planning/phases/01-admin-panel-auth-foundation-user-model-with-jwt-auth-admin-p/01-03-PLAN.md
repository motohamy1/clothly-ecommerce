# Plan 01-03: Auth UI — middleware, login page, admin chrome

<goal>
Close the end-to-end auth loop so a real admin can log in through the
browser: the `middleware.ts` Edge gate redirects unauthenticated
`/admin/**` traffic to `/admin/login` and non-admin roles to
`/admin/login?denied=1`; the `/admin/login` page renders a brand-voice
form that POSTs to `/api/auth/login`; the authenticated admin chrome
(`app/admin/(authenticated)/layout.tsx`) provides the sidebar nav, the
signed-in email, and a sign-out button that POSTs to `/api/auth/logout`
and redirects to `/admin/login`. After this plan, logging in lands on
`/admin` (the dashboard is built in Plan 01-05), and the chrome and
form use the exact copy and tokens from `01-UI-SPEC.md`.

</goal>

<context>
Per `01-CONTEXT.md` D-05 (Next.js middleware at repo root, redirect on
missing/invalid cookie and on `role !== 'admin'`), D-06 (login page at
`/admin/login`, logout via `/api/auth/logout` clears the cookie), and
D-21/D-22 (anti-slop design, 16px inputs on mobile, WCAG AA, reduced-
motion respect). The copy is fully specified in `01-UI-SPEC.md` §Copywriting
Contract and the visual tokens in §Color, §Typography, §Spacing.

The Edge middleware must use `jose` for JWT decode (`01-RESEARCH.md:156`
explains why `jsonwebtoken` would fail to bundle). The `getSession()`
helper that Plan 01-02 created in `lib/auth.ts` is the right primitive
for the server-component layout, but middleware runs on Edge and cannot
use `next/headers`'s `cookies()` — middleware must read
`request.cookies.get(COOKIE_NAME)` directly.

The `components.json` already configures shadcn (new-york style, neutral
base, `lucide` icons, `app/globals.css` for Tailwind, `@/lib/utils` for
`cn`). The `lib/utils.ts:1-6` `cn()` helper is already in place. shadcn
primitives for the login form are: `button`, `input`, `label`, `card`.
The chrome needs `button` (sign-out). These four primitives are added in
this plan; the remaining primitives for the admin product UI (table,
dialog, select, textarea, tabs, alert-dialog) come in Plan 01-05/01-06.

Per the UI-SPEC, the login page is the one signature moment on the auth
surface (a 380px-max card with a 2px warm-amber rule above the form, a
hairline border, an inset highlight on the top edge, full-width
filled-ink "Sign in" button). The admin chrome is deliberately quiet
(ink sidebar, off-white labels, active state is a 1px warm-amber left
bar + text color, no dot, no glow).

Plan 01-04 gates the existing `/api/admin/**` routes. Plan 01-05 builds
the dashboard at `/admin` (which is where the layout sends the user
after sign-in).

</context>

<task id="01-03-02">
<action>Create `middleware.ts` at the repo root (the file does not exist
yet). It is the Edge-runtime gate for every `/admin/**` URL except
`/admin/login`. The file must start with
`import { NextRequest, NextResponse } from 'next/server';` and
`import { jwtVerify } from 'jose';`. It exports
`export async function middleware(request: NextRequest)`: read
`request.nextUrl.pathname`; if it is `/admin/login` or does not start
with `/admin`, return `NextResponse.next()`; otherwise read
`request.cookies.get('clothly_session')?.value` and the secret
`process.env.JWT_SECRET`; if either is missing, redirect to
`/admin/login` (clone `request.nextUrl`, set pathname, do NOT set a
search string); otherwise call
`await jwtVerify(token, new TextEncoder().encode(secret))` inside a
try/catch — on success, check `payload.role`; if it is not `'admin'`,
redirect to `/admin/login?denied=1`; if it is admin,
`return NextResponse.next()`; on any catch (expired, invalid signature),
redirect to `/admin/login?expired=1`. Then export
`export const config = { matcher: ['/admin/:path*'] }` so the runtime
only invokes the function for `/admin/**` URLs. Do NOT import
`next/headers`'s `cookies()` — that API is not available in Edge; read
from `request.cookies` only.

Then create `app/admin/login/page.tsx` as a server component. The file
imports `redirect` from `next/navigation`, `getSession` from
`@/lib/auth`, and the default export `LoginForm` from
`@/components/admin/login-form`. It defines
`interface PageProps { searchParams: Promise<{ denied?: string; expired?: string }> }`
and exports `async function LoginPage({ searchParams }: PageProps)`:
await the `searchParams` Promise; if
`(await getSession())?.role === 'admin'`, `redirect('/admin')` (an
already-logged-in admin should not see the login page); render
`<main className="min-h-screen flex items-center justify-center bg-[#FAF7F2] px-4">` with a
`<LoginForm denied={params.denied === '1'} expired={params.expired === '1'} />` inside.

Then create `components/admin/login-form.tsx` as a `'use client'`
component. Use `useForm` from `react-hook-form`, `zodResolver` from
`@hookform/resolvers/zod`, and `z` from `zod`. Define a `loginSchema`
with `z.object({ email: z.string().email('Enter a valid email address.'),
password: z.string().min(1, 'This field is required.') })`. The
component renders a `<Card>` (from `@/components/ui/card`) styled per
the UI-SPEC §Login page: `max-w-[380px] w-full` with a 1px hairline
border (the `Card` primitive already provides one), an inset top
highlight, a 2px warm-amber rule above the form (use `<div className="h-[2px] bg-[#B8763A] mb-6" />` as a bookmark), the headline
`<h1 className="text-[28px] font-medium leading-[1.25] mb-2 text-[#1A1814]">Sign in to manage the shop.</h1>`
(per UI-SPEC §Login page headline), the helper `<p className="text-[13px] text-[rgba(26,24,20,0.6)] mb-6">Enter the email and password you set up with the team.</p>`,
then a `<form onSubmit={handleSubmit(onSubmit)} className="space-y-4">` with
email and password fields (each using shadcn `Input` and `Label`,
16px on mobile per the override in T1.1), inline error messages under
each field from `formState.errors`, and a full-width
`<Button type="submit" className="w-full bg-[#1A1814] text-[#FAF7F2] hover:bg-[#1A1814]/90 rounded-lg h-12">` with the label "Sign in". Below the form, a single
muted line `<p className="mt-6 text-[13px] text-[rgba(26,24,20,0.6)]">Need help? Reach the team at hello@clothly.test.</p>`. The
`onSubmit` handler does
`const res = await fetch('/api/auth/login', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(values) })`; on `res.ok` call `router.push('/admin')`; on failure read
`await res.json().catch(() => ({}))` and set a local `useState` `formError`
to either `'That email and password don\'t match. Try again, or reach out if you\'ve lost access.'`
(UI-SPEC §Login error) or the UI-SPEC §Login error for a missing
`JWT_SECRET` server-side ('The shop can\'t sign anyone in right now...').
Also surface the `denied` and `expired` props from the page as
top-of-card notices using the same warm-amber rule. Do NOT use
`router.push` from a hook conditionally during render — use it inside
the onSubmit callback only.

<threat_model>
<surface>Edge middleware gating `/admin/**`, the login form's POST to
`/api/auth/login`, the sign-out button's POST to `/api/auth/logout`, and
the server-component layout that re-validates the session on every
authenticated page. The auth surface itself (User model, JWT, login
endpoint) was hardened in Plan 01-02; this plan extends it with a
browser-facing flow.
</surface>
<risks>
- [S-Spoofing] A forged `role: 'admin'` JWT would be accepted by the
  middleware if `JWT_SECRET` were weak. Mitigated by the `JWT_SECRET` ≥
  32 random chars floor in `.env.example` (Plan 01-01) and the Edge
  runtime's strict `jose.jwtVerify` signature check.
- [S-Spoofing] CSRF on the logout endpoint (forcing a victim to sign out
  is low-impact but could be abused to grief). Mitigated by
  `SameSite=Lax` on the session cookie (Plan 01-02); the logout
  endpoint does not change state on the server, only clears the
  client-side cookie.
- [R-Repudiation] No audit log of who logged in or out. Deferred per
  `01-CONTEXT.md:155`.
- [E-Elevation of Privilege] The middleware skips `/admin/login` by
  design (D-05), but the server-component layout in this plan adds a
  second gate (`if (role !== 'admin') redirect('/admin/login')`) — this
  is defense in depth so a future route group change cannot bypass the
  check.
- [T-Tampering] An attacker who can read the file system can replace
  `middleware.ts`. Mitigated by standard deploy hygiene; out of scope
  for this phase.
</risks>
</threat_model>
