# Plan 01-04: Admin API auth gate + image upload route

<goal>
Lock down the existing admin proxy routes so unauthenticated requests
return 401 instead of silently proxying to the backend (D-09 — the
Next.js proxy is the trust boundary for the admin UI), and add the new
`POST /api/admin/upload` route that accepts a single image file, enforces
MIME-type and size limits, writes it under `/public/images/products/`,
and returns the public path. The admin product pages in Plans 01-05 and
01-06 use this route to populate `images[]` and the primary `image` field.

</goal>

<context>
Per `01-CONTEXT.md` D-09 (every `/api/admin/**` server route verifies the
JWT cookie before proxying to the backend — the backend is auth-unaware
in this phase). Per D-18 (drag-and-drop or click-to-pick, uploaded to
`POST /api/admin/upload`, saved under `/public/images/products/{timestamp}-
{slug}.{ext}`, returns the public path). The pattern for Next.js route
handlers is at `app/api/admin/products/route.ts:1-25` (already exists;
the executor only needs to add the auth gate at the top of each handler).

The `requireAdmin()` helper from Plan 01-02 in `lib/auth.ts` is the
single primitive the gate uses. The Image upload route uses the
Edge/Node `request.formData()` API (no `multer`/`formidable` per
`01-RESEARCH.md:311`).

The verify step for ADMIN-08 (`/api/admin/**` rejects unauthenticated)
relies on this plan's gate. The form-driven image upload in Plan 01-06
relies on this plan's upload route. The `app/error.tsx` clear-error
boundary comes in Plan 01-07 with the storefront migration.

</context>

<task id="01-04-02">
<action>Create `app/api/admin/upload/route.ts` as a new Next.js route
handler. The file imports `NextResponse` from `next/server`,
`requireAdmin` from `@/lib/auth`, `writeFile` and `mkdir` from
`node:fs/promises`, the default `path` from `node:path`, and the
default `crypto` from `node:crypto`. At the top of the file, declare two
module-level constants: `const ALLOWED_TYPES = new Set(['image/jpeg',
'image/png', 'image/webp'])` and `const MAX_BYTES = 5 * 1024 * 1024`
(5 MB cap per D-18 and `01-RESEARCH.md:651`).

Export `async function POST(request: Request)`. The body of the handler
runs these steps in order, with the `try { ... } catch` shape mirroring
`app/api/admin/products/route.ts:8-14`:

1. Gate: `try { await requireAdmin(); } catch (response) { return response as Response; }` — unauthenticated callers never reach the upload logic.

2. Parse: `const form = await request.formData(); const file = form.get('file'); if (!(file instanceof File)) return NextResponse.json({ error: 'No file provided' }, { status: 400 });`.

3. Validate: if `!ALLOWED_TYPES.has(file.type)` return
`NextResponse.json({ error: 'Only JPEG, PNG, or WebP allowed' }, { status: 400 })` (UI-SPEC §Image upload error: "That file type isn't supported. Use a JPG, PNG, or WebP."). If `file.size > MAX_BYTES` return
`NextResponse.json({ error: 'File too large (max 5MB)' }, { status: 400 })`.

4. Slug + filename (D-18: `{timestamp}-{slug}.{ext}`): `const ext = path.extname(file.name).toLowerCase() || '.png'; const base = path.basename(file.name, ext).toLowerCase().replace(/[^a-z0-9]+/g, '-').slice(0, 40); const filename = `${Date.now()}-${crypto.randomUUID().slice(0, 8)}-${base}${ext}`. The `crypto.randomUUID().slice(0, 8)` suffix prevents collisions if two uploads land in the same millisecond (Pitfall 8 in `01-RESEARCH.md:902-905`).

5. Write: `const dir = path.join(process.cwd(), 'public', 'images', 'products'); await mkdir(dir, { recursive: true }); const bytes = Buffer.from(await file.arrayBuffer()); await writeFile(path.join(dir, filename), bytes);`.

6. Respond: `return NextResponse.json({ path: `/images/products/${filename}` }, { status: 200 });`.

The file size and MIME checks happen BEFORE the write, so a rejected
file never lands on disk. The `mkdir { recursive: true }` is idempotent
so the directory creation is safe to repeat.

</action>

<threat_model>
<surface>Two new attack surfaces: the auth gate on the existing admin
proxy (deny-by-default) and the new upload route (file ingest from an
authenticated admin). The gate is a single line per handler; the upload
route is the larger concern.
</surface>
<risks>
- [E-Elevation of Privilege] An unauthenticated request to
  `/api/admin/**` could be silently proxied to the backend, exposing
  the catalog. Mitigated by the explicit `requireAdmin()` gate at the
  top of every handler (deny by default, no implicit allow).
- [T-Tampering] Path traversal in the upload filename: a malicious
  filename like `../../etc/passwd` could escape `public/images/`.
  Mitigated by the slug regex `replace(/[^a-z0-9]+/g, '-')` which
  strips all slashes and dots, plus the `Date.now()-` and
  `randomUUID().slice(0, 8)` prefixes that put only safe characters in
  the leading path. The `path.join` then resolves under `public/`
  safely.
- [D-Denial of Service] Large file uploads filling the disk. Mitigated
  by the 5MB `MAX_BYTES` cap; the body is read into a `Buffer` only
  after MIME and size checks pass.
- [T-Tampering] Uploading a file with a misleading MIME type (e.g. a
  renamed `.exe` with `image/jpeg`). Mitigated at the application
  layer by trusting the client-supplied `file.type` for now (the
  alternative — magic-byte sniffing — adds a dependency and is deferred
  per `01-CONTEXT.md:153`'s "Out of scope" list). The risk is bounded
  by the fact that the file is served from `/images/products/` as a
  static asset and the Next.js server never executes it.
- [I-Information Disclosure] The new file lives at a public URL
  immediately. If a future change ever generates signed/time-limited
  URLs for the storefront, the upload path would need to be revisited.
  Out of scope for this phase.
</risks>
</threat_model>
