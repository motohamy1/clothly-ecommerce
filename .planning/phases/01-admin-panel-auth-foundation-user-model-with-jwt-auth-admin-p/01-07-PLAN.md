# Plan 01-07: Storefront migration — backend reads, seed:products, error boundary

<goal>
Cut the storefront over to the live backend so admin edits are visible
to the public site on next visit: move the seed dataset from
`lib/products.ts` to a new `lib/product-seeds.ts` (single source of
truth for seeds), reduce `lib/products.ts` to types only (the mutating
helpers — `getProductById`, `getCollection`, `getProductSection`,
`getProductsBySection`, `getRelatedProducts`, `catalog`, `allProducts`
— are deleted), add the `seed:products` script in the backend that
bulk-writes the 33-product seed set via `ProductModel.bulkWrite` (D-12),
switch every storefront read off the static file and onto
`backendFetch('/shop/...')` (the home page does not read products per
`app/page.tsx:1-14`; the migration touches `app/api/products/*`,
`app/product/[id]/page.tsx`, `components/CategoryPage.tsx`,
`components/SideBar.tsx`, and `lib/admin.ts`), add an
`app/error.tsx` boundary so a backend outage renders the honest
error state (D-12: "clear error state, not stale data" — no fallback
to the static catalog), and patch `components/SideBar.tsx` to derive
the active section from the product slug prefix (the `getProductSection`
helper is gone with the static catalog). After this plan, killing the
backend and refreshing `/men` shows the brand-voice error, not stale
data.

</goal>

<context>
Per `01-CONTEXT.md` D-11 (every storefront read currently in
`lib/products.ts` migrates to `backendFetch('/shop/...')`), D-12
(`lib/products.ts` is kept as the seeding source-of-truth via the
`product()` builder and the seed arrays; the static file becomes
read-only with no fallback path; backend unreachable → clear error
state), D-13 (all new storefront fetches use `cache: 'no-store'`,
already the `backendFetch` pattern), and the per-component
file:line migration map in `01-CONTEXT.md:90-98` and
`01-RESEARCH.md:872-886`.

The current `lib/products.ts:1-184` exports the types AND the catalog
arrays AND the mutating helpers. The migration deletes the catalog and
helpers and keeps only the types. The `product()` builder and its
supporting arrays (`productImages`, `coreVariants`, `apparelSizes`,
`mensSizes`, `kidsSizes`, `adultShoeSizes`, `womensShoeSizes`,
`kidsShoeSizes`, `gallery`) move to `lib/product-seeds.ts`. The
backend's `seed:products` script imports the seed set from
`lib/product-seeds.ts` via a relative path — the backend's
`tsconfig.json` `rootDir` is `"./src"` so the import resolves from
outside the `src` tree; this plan updates `backend/tsconfig.json` to
add `"rootDirs": ["./src", "../lib"]` so ts-node can resolve the
import (the `tsc` build still emits to `dist/`, so this is a
type-checker-and-runtime setting, not a build-output setting). The
`seed:products` script runs via `ts-node` (not via the built `dist/`)
because the cross-package import is a dev-time concern.

`components/CategoryPage.tsx:14-15` is a `'use client'` component that
calls `getCollection(section)` synchronously. Converting it to a
server component that `await backendFetch('/shop/' + section)` lets
the page render the live data; the styled-components `StyledWrapper`
keeps working in server components. The collection's `label` and
`headline` (currently in `lib/products.ts:77-78, 100-101, 123-124`)
are not in the backend's response — they move to a new
`lib/collection-meta.ts` (per `01-RESEARCH.md:1086-1087`).

`components/SideBar.tsx:6, 33` imports `getProductSection` and uses
it to map a product URL to a section. The seeded product slugs all
start with `men-`, `women-`, or `kids-` (per the existing
`lib/products.ts:81-139` IDs); the new admin form requires a slug
matching `/^[a-z0-9-]+$/` (Plan 01-06). The simplest replacement is a
slug-prefix parser — a 6-line helper that does what `getProductSection`
did, with the documented assumption that admin-created slugs use the
section prefix. The executor must add a comment in the code that
documents this constraint.

The `lib/admin.ts:14` `fetch('/api/admin/products')` is a relative URL
that doesn't work in server components (Pitfall 6 in
`01-RESEARCH.md:888-893`); this plan replaces it with `backendFetch(
'/shop/products')` directly. The function's return shape is unchanged.

The honest error state per D-12 is an `app/error.tsx` boundary that
renders a page-level message ("Our shop is taking a moment. Try again
in a minute.") when a server component throws (e.g. a `backendFetch`
failure surfaces as a render error caught by the boundary). The
`app/product/error.tsx` adds a per-route boundary for product detail.
Both use the brand-voice copy; no fabricated "X products available"
widget. The previous static `lib/products.ts` data must NOT be
displayed as a fallback — this is the explicit D-12 prohibition.

</context>

<threat_model>
<skip_if>low-risk utility work, no auth surface, no external input</skip_if>
<surface>The storefront reads from the backend (which is in the same trust
domain as the storefront — both run on the Next.js origin). The new
`seed:products` script is a developer-only CLI, not an HTTP endpoint.
The error boundary is a UI artifact. No new auth surface, no new
public input.
</surface>
<risks>
- [I-Information Disclosure] The new error boundary might surface a
  backend error string to the public. Mitigated by the boundary's
  copy: it shows the brand-voice message, not the raw error. The
  underlying `error.message` is logged to the server's console
  (Next.js default) but not rendered in the page.
- [D-Denial of Service] A backend outage now visibly fails the
  storefront instead of falling back to the static catalog. This is
  the explicit D-12 trade-off: the storefront renders an honest
  error state, not stale data, so the operator is forced to notice
  and fix the backend. The `cache: 'no-store'` setting (D-13) means
  every request is a fresh fetch; no stale data is served from a
  cache layer.
- [E-Elevation of Privilege] The new `seed:products` script can
  overwrite or insert any product. Mitigated by the script being a
  developer-only CLI (no HTTP exposure) and by the `upsert: true`
  shape being a no-op for products with matching IDs.
- [T-Tampering] The slug-prefix parser in `SideBar` could mis-categorize
  an admin-created product whose slug does not start with
  `men-`/`women-`/`kids-`. Mitigated by the slug-format zod rule
  (`/^[a-z0-9-]+$/`) combined with the documented code comment that
  says "fail-soft" (the sidebar simply does not highlight a section
  for an unmatched slug).
</risks>
</threat_model>
