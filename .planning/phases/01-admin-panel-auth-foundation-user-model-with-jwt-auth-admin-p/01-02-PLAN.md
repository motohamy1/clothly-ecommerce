# Plan 01-02: Server-side auth — User model, JWT, login/logout, seed

<goal>
Stand up the full server-side auth surface that Plan 01-03 will gate behind
the Edge middleware: a Mongoose `User` model (bcrypt-hashed password, never
serialized), an Express `auth` router mounted at `/auth` with
`POST /auth/login` and `POST /auth/logout` (issuing and clearing the
`clothly_session` httpOnly cookie), the `seed:admin` script that idempotently
upserts the first admin from `ADMIN_EMAIL`/`ADMIN_PASSWORD`, a frontend
`lib/auth.ts` with `getSession`/`requireAdmin` (using `jose`), and the
Next.js proxy route handlers at `/api/auth/login` and `/api/auth/logout`
that mirror the Express endpoints. No UI yet — the curl loop must work
end-to-end before the login page is built in Plan 01-03.

</goal>

<context>
The auth decisions in `01-CONTEXT.md` D-02 through D-09 are all honored
here: hand-rolled JWT (D-02), Mongoose `User` with `select: false` on
password and `lowercase: true` on email (D-03), `clothly_session` httpOnly
cookie signed by `JWT_SECRET` (D-04), Express `auth` router at `/auth`
(D-08), `seed:admin` script as the only admin-creation path (D-07), and
the Next.js proxy is the trust boundary for `/api/admin/**` (D-09; the
proxy gate is added in Plan 01-04).

The Mongoose model pattern to mirror is at `backend/src/models/product.ts:1-64`
(interface + new Schema + `set('toJSON', ...)` + `mongoose.model`). The
Express router pattern to mirror is at `backend/src/routers/clothes.ts:51-71`
(async handlers, `try { ... } catch (err) { return next(err) }`). The
`backendFetch` helper at `lib/backend.ts:7-22` is the pattern for the
Next.js proxy route handlers.

The env contract from Plan 01-01 is in place: `JWT_SECRET` exists and the
backend fails fast if it is missing. The new deps (`jsonwebtoken`, `bcrypt`,
`@types/*`, `jose`) are installed.

Plan 01-03 builds the login page and the `middleware.ts` that calls
`getSession()` from `lib/auth.ts`. Plan 01-04 wires `requireAdmin` into
the existing `/api/admin/**` route handlers.

</context>

<action>Create the `User` Mongoose model at `backend/src/models/user.ts`,
mirroring `backend/src/models/product.ts:1-64` exactly. The file exports a
`UserRole` type alias of `'admin' | 'customer'`, a `UserDocument` interface
extending `mongoose.Document` with `email: string`, `password: string`,
`role: UserRole`, `createdAt: Date`, `updatedAt: Date`. The schema
definition uses `new Schema<UserDocument>({...}, { timestamps: true,
versionKey: false })`: `email` is `{ type: String, required: true, unique:
true, lowercase: true, trim: true, index: true }`; `password` is
`{ type: String, required: true, select: false }` (the `select: false`
keeps the hash off the default `.find()` projection — D-03's
"never returned in JSON"); `role` is `{ type: String, required: true,
enum: ['admin', 'customer'], default: 'customer' }`. The schema's
`toJSON` transform must strip `password` defensively (even though
`select: false` already protects most paths) — set
`userSchema.set('toJSON', { transform: (_doc, ret) => { const { _id,
password, ...json } = ret.toObject ? ret.toObject() : ret; void _id;
void password; return json; } })`. Export
`export const UserModel = mongoose.model<UserDocument>('User', userSchema)`.
The `'use strict'` CommonJS style (matches `backend/src/index.ts:1-2`'s
double-quote strings, no semicolons omitted) must be followed.

Then create `backend/src/routers/auth.ts` that exports `default router`
and mounts two handlers, each following the `clothes.ts:51-71` async-try-
catch-next pattern. `POST /auth/login` (handler: `async (req, res, next)`):
read `email` and `password` from `req.body`, lowercase and trim the email
exactly as the schema would, call
`UserModel.findOne({ email }).select('+password')` to force the hash
inclusion, call `bcrypt.compare(password, user.password)`, fail with
`res.status(401).json({ error: 'Invalid email or password' })` if no user
or the compare fails, then sign a JWT with `jsonwebtoken`'s `jwt.sign(
{ sub: user._id.toString(), email: user.email, role: user.role },
process.env.JWT_SECRET, { algorithm: 'HS256', expiresIn: '7d' })`, set
the cookie via `res.cookie('clothly_session', token, { httpOnly: true,
sameSite: 'lax', secure: process.env.NODE_ENV === 'production', path:
'/', maxAge: 7 * 24 * 60 * 60 * 1000 })` (D-04: httpOnly, SameSite=Lax,
Secure in prod, path=/, 7-day expiry), and respond
`res.status(200).json({ ok: true, user: { email: user.email, role:
user.role } })`. `POST /auth/logout`: call
`res.clearCookie('clothly_session', { path: '/' })` and respond
`res.status(200).json({ ok: true })`. Do NOT mount the router yet — that
is part of the next sub-action. Validate that `email` and `password` are
non-empty strings before hitting Mongoose; reject with 400 otherwise.

</action>

the executor must add it). This module is the only place the Next.js
runtime decodes and verifies the `clothly_session` JWT. It exports a
`SessionUser` interface (`{ sub: string; email: string; role: 'admin' |
'customer' }`), a `COOKIE_NAME` constant of `'clothly_session'`, an async
`getSession()` that reads the cookie via `await cookies()` from
`next/headers`, calls `jose.jwtVerify(token, new TextEncoder().encode(
process.env.JWT_SECRET))` (with `process.env.JWT_SECRET ?? ''` — empty
secret will fail the verify, which is the desired safe-fail), and returns
`{ sub, email, role }` or `null`, and an async `requireAdmin()` that calls
`getSession()` and throws a `Response` with status 401 (or returns a
`NextResponse.json({ error: 'Unauthorized' }, { status: 401 })` — pick
ONE consistent shape and document it in a JSDoc comment) when the session
is missing or `role !== 'admin'`. The `getSession()` must return `null`
on any decode failure (expired, invalid signature, missing cookie, missing
secret) — never throw. Use `jose` from the root `package.json` (already
installed in Plan 01-01).

Then create `app/api/auth/login/route.ts` and
`app/api/auth/logout/route.ts` — the Next.js proxy endpoints the admin
UI will hit (per D-09, the Next.js proxy is the trust boundary for the
admin UI, but auth endpoints are mirrored here for symmetry and so the
`SameSite=Lax` cookie is set on the same origin as the page that reads
it). Both files import `NextResponse` from `next/server` and
`backendFetch` from `@/lib/backend`. `app/api/auth/login/route.ts`
exports `async function POST(request: Request)` that reads the JSON body
via `await request.json()`, calls
`backendFetch('/auth/login', { method: 'POST', body: JSON.stringify(body)
})`, forwards the backend's `Set-Cookie` header from the response (read
`response.headers.get('set-cookie')` if you have to wrap the backend
call in a manual `fetch` — OR change `backendFetch` to return the
`Response` object so the headers are accessible; the simplest is to add

do not modify `backendFetch`'s contract), and respond 200 with

function shape MUST stay `async function POST(request: Request)` per
Next.js App Router conventions.

<threat_model>
<surface>This plan introduces the entire auth attack surface for the
phase: a User model, password hashing, JWT signing/verification, login
and logout endpoints, a seed script, and the frontend decode helper.
The first three are the most security-sensitive. The admin login is the
only login UI in the phase; the only role is `admin` (the seed script
always assigns it).
</surface>
<risks>
- [S-Spoofing] Credential stuffing or brute force on `POST /auth/login`. The
  plan does NOT add rate limiting (deferred per the
  `01-RESEARCH.md:1226-1227` rate-limit note and per the "Deferred Ideas"
  list in `01-CONTEXT.md:153`). Mitigation: short password length floor
  (12 chars) in the seed script; logged audit-friendly errors (`Invalid
  email or password` not `Unknown email`); `JWT_SECRET` must be ≥ 32
  random bytes in production (the `.env.example` documents this).
- [S-Spoofing] JWT secret brute force. Mitigated by the boot-time
  `JWT_SECRET` fail-fast added in Plan 01-01 and by the ≥ 32-char
  recommendation in `.env.example`. The HS256 algorithm uses a single
  shared secret; 32+ random bytes is the standard floor.
- [I-Information Disclosure] `password` hash leaking through a forgotten
  projection. Mitigated at three layers: schema-level `select: false` on
  `password`; `toJSON` transform that strips `password` defensively; the
  login handler uses an explicit `.select('+password')` only at the
  compare site and never returns the user object directly (it returns
  `{ email, role }` only).
- [T-Tampering] Mass-assignment creating a user with `role: 'admin'`
  through the public registration path. Mitigated by D-07: there is NO
  public registration endpoint in this phase. The `seed:admin` script is
  the only admin-creation path, and the Express login endpoint never
  creates users.
- [R-Repudiation] No audit log of login attempts. Deferred per
  `01-CONTEXT.md:155` (audit log is a follow-up).
- [E-Elevation of Privilege] A cookie theft grants full admin access
  until the 7-day expiry. Mitigated by `httpOnly: true` (JS can't read
  the cookie) and `SameSite=Lax` (most CSRF blocked). Token revocation
  is out of scope for v1; the customer-auth follow-up phase may add a
  blacklist.
- [S-Spoofing] `getSession()` could be called with `JWT_SECRET` undefined
  in dev. Mitigated by the fail-fast in Plan 01-01: the backend will
  not start without it. `lib/auth.ts` defends in depth by treating
  undefined secret as a verify failure (returns `null`).
</risks>
</threat_model>
