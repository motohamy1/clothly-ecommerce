# Plan 01-08: Hygiene verification + full manual UAT pass

<goal>
Close the phase with a 20-step manual UAT pass (per
`01-VALIDATION.md` §Manual Test Plan) that walks every requirement
end-to-end, and re-verify the three hygiene items (`HYGIENE-01` start
script, `HYGIENE-02` `MONGODB_URI` production warning, `HYGIENE-03`
`tsconfig.json` `backend` exclude). Any gap found during the UAT
becomes a small follow-up edit (touched in this plan, not a new plan).

that records every step's outcome, every gap and its fix, and a final
"all green" sign-off.

<task id="01-08-01">
<action>Run the 20-step manual UAT pass from `01-VALIDATION.md:1183-1204`
in order. For each step, record the outcome (pass / fail / N/A) and
the exact command output or the manual observation. The 20 steps are:

1. `cd backend && npm install && npm run dev` — backend starts with no errors. The "Connected to MongoDB" line and "Server is running on port 5000" line both appear.
2. `cd backend && ADMIN_EMAIL=admin@clothly.test ADMIN_PASSWORD='clothly-admin-pass-12' npm run seed:admin` — admin user is upserted. Output includes the "Admin upserted:" log line.
3. `cd backend && npm run seed:products` — 33 products upserted. Output includes the "Seeded 33 products" line. (If Plan 01-07's `seed:products` script was wired correctly, this is the seed step.)
4. `npm run dev` at the repo root — frontend starts with no errors.
5. Verify the storefront without logging in: visit `/men`, `/women`, `/kids`, `/product/<id>` for any seeded product. Each page renders the live product data from MongoDB. Then kill the backend and refresh — the page renders the brand-voice error ("The shop is taking a moment"), NOT stale data.
6. Visit `/admin` without logging in — redirected to `/admin/login`.
7. Forge a `clothly_session` cookie with a `role: 'customer'` payload (sign a JWT with the same `JWT_SECRET` but `role: 'customer'`) and visit `/admin` — redirected to `/admin/login?denied=1`.
8. Log in at `/admin/login` with the seeded admin creds — redirected to `/admin`. The dashboard shows the real stats (33 total, with the correct per-section breakdown).
9. Visit `/admin/products` — the table shows all 33 seeded products.
10. Click "New product" — the create form renders with all four tabs (Basics, Images, Sizes, Variants).
11. Fill the form (a unique slug, name, price, primary image path, category, group, section, description, a couple of sizes, a couple of variants) and click Save. The form redirects to `/admin/products` and the new product is visible in the table.
12. Click the new product to edit — the edit form pre-populates with the saved values.
13. Drop a small (under 5MB) JPG on the image dropzone on the Images tab — upload succeeds, a preview appears, the file lands on disk under `public/images/products/`, and the form binds the returned path into `images[]`. Save the form.
14. Add a sizes row, save — the `sizes` array updates.
15. Add a variant row, save — the `variants` array updates.
16. Edit the product's name in the Basics tab, save — visit `/product/<slug>` and confirm the new name appears.
17. Click Remove on the product row in the list — the AlertDialog appears with the brand-voice title and body. Confirm — the row disappears from the list AND the product is gone from the storefront (`/product/<slug>` triggers `notFound()`).
18. Click "Sign out" in the sidebar — redirected to `/admin/login`. Visiting `/admin` again redirects to login.
19. Re-login at `/admin/login` with the same admin creds — works (proves the cookie-clearing was client-side and re-login creates a fresh session).
20. Manually set a JWT in the cookie with `exp: <past timestamp>` and visit `/admin` — redirected to `/admin/login?expired=1`.

For every step that fails, record: the step number, the observed

suspected cause (cite the file:line if you can), and the planned fix.

<task id="01-08-02">
<action>For each UAT step recorded as "fail" in the previous task,
apply the minimum fix that satisfies the step. Use `Edit` (not
`Write`) for any existing file; the executor must read the file
before editing. Common likely gaps and their fixes (the executor
should diagnose first, not assume):

- Step 5 stale-data leak: confirm `app/error.tsx` and
  `app/product/error.tsx` do NOT import or reference any data from
  `lib/products.ts` (which is now types-only and has no data to
  fall back to anyway, but the error boundary must not call any
  fetcher that would re-introduce stale data). Confirm
  `app/api/products/route.ts` does NOT have a try/catch that
  catches the error and serves the static catalog.
- Step 7 customer-cookie redirect: confirm `middleware.ts` does
  `if (payload.role !== 'admin') redirect('/admin/login?denied=1')`
  on the success branch of `jwtVerify`. If the success path falls
  through to `NextResponse.next()` without the role check, fix it.
- Step 8 dashboard counts: confirm `lib/admin.ts` uses
  `backendFetch('/shop/products')` (the Plan 01-07 fix). If the
  relative `fetch('/api/admin/products')` slipped through, the
  dashboard's `connected: false` fallback fires and shows 0s.
- Step 13 image upload: confirm the file landed at
  `public/images/products/{timestamp}-{uuid8}-{slug}.{ext}` and the
  form's `images[]` row shows the path. If the path is missing,
  the dropzone's `onUploaded` callback did not wire into the
  `useFieldArray` `append`.
- Step 16 storefront reflection: confirm
  `app/product/[id]/page.tsx` and `app/api/products/[id]/route.ts`
  use `cache: 'no-store'` (the `backendFetch` default — passing
  it explicitly is harmless but not required). The storefront
  reflection is also a function of `revalidate = 0` on any
  non-`backendFetch` fetches in the app tree; the storefront
  migration in Plan 01-07 removed all such fetches.
- Step 17 delete round-trip: confirm the `AlertDialog` confirm
  handler calls `fetch('/api/admin/products/${id}', { method:
  'DELETE' })` and that the row UI updates on success (via
  `router.refresh()`).
- Step 20 expired-token redirect: confirm `middleware.ts` wraps
  the `jwtVerify` call in a try/catch and redirects to
  `/admin/login?expired=1` on any error.

Re-run the failing steps after each fix until they pass. Record each
fix in the SUMMARY.md with the file:line changed and the step that
the fix resolved. If a fix is non-trivial (touches more than two
files or adds a new dependency), STOP and write a short note in the
SUMMARY describing why a follow-up plan is needed rather than
inflating this one.

</action>
